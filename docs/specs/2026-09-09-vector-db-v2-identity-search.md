## 1. TL;DR

從「檔案搜尋」升級為「知識檢索」。三件套：

1. **身份嵌入（Identity Embedding）**：嵌入文字 = 資料夾路徑 + 檔名 + 資料夾上下文 + 任務血緣 + 內容。寫入時一次到位，向量本身帶身份——搜「鹿角蕨」時「千手皇冠」的照片能被語意命中（不只靠 FTS 兜底）。
2. **分組檢索（Grouped Search）**：搜尋結果不再散落噴出，按資料夾分組：資料夾卡（名稱＋命中數＋總檔數）→ 點開看該資料夾內命中檔案。搜「鹿角蕨」→ 先看到 9 種品種資料夾，點「千手皇冠」→ 7/20 檔案與鹿角蕨有關。
3. **模式差異化**：四模式從「結果都一樣」到真正不同（§4）。

## 2. 身份嵌入——五因素進向量

Blue 拆解的「一個檔案會被搜到的原因」，全部織進嵌入文字：

| # | Blue 的因素 | 資料來源 | 嵌入文字裡的形態 |
|---|---|---|---|
| 1 | 檔名 | file_path | 原檔名 |
| 2 | 資料夾名字 | file_path | `[資料夾: 01_現況紀錄/照片紀錄/營本部/Blue陽台/千手皇冠]`（昨天已做） |
| 3 | 資料夾產生的原因與上下文 | **folder_origin 新表** | `[分類: 鹿角蕨品種照]` |
| 4 | 排程任務/agent 任務性質 | task_asset_links 反查 | `[任務: 晨間巡查]` |
| 5 | 內容＋屬性聯動 | 視覺描述/檔案內容 ＋ **topic_terms 新表** | `[屬性: 植物/蕨類/鹿角蕨]` ＋ 內容主體 |

**組合公式**：

```
embed_text = [資料夾: {路徑}] [分類: {folder_origin.category}] [主題: {folder_origin.summary}]
             [任務: {task.name}] [屬性: {topic_terms}] {檔名} {內容前2000字}
```

每段可選（無則跳過）——流水編號照片也有資料夾身份，任務產出有任務血緣。

### 2.1 folder_origin 表（資料夾的分類身份）

```sql
CREATE TABLE folder_origin (
  folder_path TEXT PRIMARY KEY,  -- 相對路徑
  root TEXT NOT NULL,
  category TEXT,                 -- 人類分類：鹿角蕨品種照/巡查筆記/IG發想文…
  summary TEXT,                  -- 一句話主題
  origin_kind TEXT,              -- user / task / agent
  task_id TEXT,
  updated_at INTEGER
);
```

**怎麼填（三路合一）**：
1. **規則推斷**（免 LLM，立即可用）：路徑模式 → 分類。`照片紀錄/**/<品種名>` → 品種照；`*IG*.md` → IG 發想文；`*巡查*` → 巡查筆記
2. **任務反查**：task_asset_links（4 筆）回填 origin_kind=task + 任務名
3. **LLM 蒸餾**（增強，後續）：同資料夾檔案摘要 → 主題一句話

### 2.2 任務上下文

寫入時（MediaIngestHook/排程產出）查 task_asset_links → 帶 `[任務: ...]`。4 筆既有連結重嵌時自動帶上。資料會隨任務累積。

### 2.3 屬性聯動（灑水系統 → 鹿角蕨）

語意向量天然能做概念關聯，但跨域詞（灑水↔農業生產）需要**主題詞表**：

```sql
CREATE TABLE topic_terms (
  term TEXT PRIMARY KEY,   -- 鹿角蕨
  related TEXT,            -- JSON: ["植物","蕨類","農業","照顧","品種"]
  updated_at INTEGER
);
```

**冷啟動**：從 6,140 筆 tags 蒸餾（千手皇冠→鹿角蕨 的「品種→物種」關聯：同資料夾照片 tags 都有品種名，品種資料夾共同出現在鹿角蕨相關內容中）。**查詢擴展**：搜「鹿角蕨」→ 擴展 {鹿角蕨, 植物, 蕨類, 農業照顧} → 灑水工作流（主題詞含農業）也命中。

## 3. 排序——Blue 五因素順序

```
final_score = 0.30·name_hit      ← 因素1：檔名直接命中
            + 0.25·folder_hit    ← 因素2：資料夾路徑命中
            + 0.20·context_hit   ← 因素3：分類/主題命中
            + 0.15·task_hit      ← 因素4：任務血緣命中
            + 0.10·semantic_hit  ← 因素5：語意相似（歸一化 0-1）
```

- name/folder/context/task hit = 0 或 1（查詢詞是否命中該欄位，FTS 判定）
- 權重初始值依 Blue 順序（1>2>3>4>5），上線後按實測調
- **re-rank 層**：HybridSearch 拿到候選後加權重排——不改既有召回，只改排序

## 3.5 呈現——資料夾分組

搜尋結果 UI 改為兩層：

```
搜「鹿角蕨」（24 筆命中，分佈 7 個資料夾）
├── 📁 Blue陽台/千手皇冠（7/20 檔案相關）  ← 展開看 7 筆
├── 📁 Blue陽台/雷電（3/12）
├── 📁 Blue陽台/象耳鹿角蕨母株（9/9）
├── 📁 06_AI協作與知識庫/鹿角蕨研究（5/30）
├── 📁 memories（記憶 3 筆）
│   …
└── 🗂 散檔（不在資料夾的直接命中 2 筆）
```

- 資料夾卡：名稱＋相關數/總數＋排序分（組內最高分）
- 點資料夾 → 展開該組命中（組內按 final_score 排）
- 資料夾排序 = 組內最高 final_score
- memories 命中獨立一組（它們沒有檔案系統身份）

## 4. 四模式重新定義（真差異化）

| 模式 | 召回 | 排序 | 用途 |
|---|---|---|---|
| **全部（All）**（新預設） | FTS＋語意＋查詢擴展（topic_terms） | **五因素加權**（§3） | 日常入口——Blue 說的「按照次序呈現」 |
| **全文** | 純 FTS（含資料夾身份文字） | BM25 | 精確字面（編號、名稱） |
| **語意** | 純向量 | 語意分 | 「概念」搜尋（模糊描述） |
| **標籤** | tags 篩選 | 標籤重疊數 | 已知分類瀏覽 |

- 「全部」= 現在的 hybrid 改名＋加權重排＋查詢擴展＋分組呈現
- UI：模式選單改名「全部」為預設第一項
- 結果標頭顯示 `N 筆命中 · 分佈 M 個資料夾`
