## 0. 為什麼要這份設計（實證動機，2026-09-17 驗屍）

`causal_ledger.db` 353 筆工具呼叫的鐵證：

| 發現 | 數據 | 含義 |
|---|---|---|
| compass_seek/read 呼叫數 | **0 次** | Agent 從不主動查羅盤——不是不乖，是沒有觸發機制 |
| 器官覆蓋率 | **9/43 有規則，34 裸奔** | canvas 家族（他最常撞牆處）零規則——查了也空手 |
| compass_meta.intent_index | **不存在**（lazy seed 從未觸發） | 檢索層＝沒上膛的槍 |
| 撞牆熱點 | canvas_add_node 敗 5 次、ui_navigate 敗 3 次 | 79 次 read_source_file 蠻力考古＝羅盤缺藥的直接代價 |

**結論：三個獨立缺陷——沒藥（內容）、沒上膛（檢索）、沒出診（觸發）。三刀一起補，缺一即回到現狀。**

## 1. 設計總綱：軍醫三件套

```
┌─────────────────────────────────────────────────┐
│  藥箱（Content）   90% 常見傷的藥預先備齊        │
│  出診（Trigger）   動手前藥自動出現在眼前        │
│  長藥（Growth）    治好的傷自動變成新藥          │
└─────────────────────────────────────────────────┘
```

Blue 定調：**不是踩一坑填一坑，是系統性預覆蓋——先讓軍醫帶上 90% 的藥，不足的再靠傷口自癒循環補。**

## 2. 藥箱：系統性預覆蓋計畫（Content Stocking）

### 2.1 覆蓋原則：按「咽喉點」而非按「器官」覆蓋

43 器官不必均勻撒藥。藥要放在 **agent 一定會經過的咽喉點** 上。實測 353 次呼叫的咽喉點排序：

| 咽喉點 | 呼叫量 | 對應器官 | 現況 | 必備的藥 |
|---|---|---|---|---|
| run_terminal | 97 | agent.tools | 裸奔 | 終端鐵則（安全掃描、timeout、&&短路坑） |
| canvas_get_state | 83 | canvas.engine | 裸奔 | 雙 store 正宮路徑、快照治理（只留最新） |
| read/patch_source_file | 86 | agent.tools | 裸奔 | 檔案→器官映射表、大檔禁全讀、AGENTS.md 錨點 |
| canvas_add_node | 11 | canvas.engine | 裸奔 | 生成節點必帶 prompt、canvas_place 註冊名≠檔名 |
| ui_navigate | 3 | theme/chat | 裸奔 | 導航鏈 audit、返回 canPop 鐵則 |
| compass_seek | (0) | compass 本身 | — | 檢索種子 |

### 2.2 藥的三種劑型（沿用三層所有權，擴充內容來源）

1. **事實卡（facts，自動採集唯寫）**——擴充 `compass_harvest`：從 codebase 自動採集「檔案→器官」映射、gate 家族清單、DB 路徑表、MCP 端點表。每週自動刷新，agent 問「X 在哪」永遠有新答案。
2. **規則卡（rules，共治）**——每條強制 why＋執行機制欄。內容來源＝**蒸餾搬運**（見 2.3）。
3. **坑卡（pitfalls）**——目前全庫只有 13 條（全在 computeruse）。要把既有教訓搬進來＋傷口自癒自動立案（見第 4 節）。

### 2.3 最大的藥源：Hermes skill 庫的蒸餾搬運

過去三個月所有撞牆教訓（幾百條 pitfalls）存在**我（小葵）的 Hermes skill 庫**，不在 App 羅盤裡——這就是「藥在別家藥局」的病灶。解法：**一次性系統性蒸餾搬運**：

- 來源：`bridge-app` skill 的 200+ references、`APP_ARCHITECTURE_MAP.md`（人工地圖的精華）、88 份 docs 的鐵則段
- 蒸餾規則（沿用素描 LLM 蒸餾層的教訓）：LLM 只補洞、規則優先、fail-open 必留錯誤痕跡
- 每條藥入庫格式：`症狀（白話）→ 病根 → 藥方 → 執行機制 → 出處（git/skill reference）`
- 搬運清單按 2.1 的咽喉點排序：**先搬 agent 會踩的，再搬冷的**

### 2.4 覆蓋率目標

| 階段 | 目標 | 驗收 |
|---|---|---|

| S2 | 34 裸奔器官全部有「事實卡＋導航錨點」（沒規則也至少有地圖） | compass_seek 每器官不再回空 |
| S3 | 藥箱飽和度＝90% 常見傷可解（紅隊出題驗證，見 5.2） | 紅隊命中率 |

## 3. 出診：觸發鏈接線（Trigger Wiring）

### 3.1 三個自動出診點（掛咽喉點，不靠自覺）

| 觸發點 | 時機 | 動作 |
|---|---|---|
| **動手前** | patch_source_file / read_source_file / canvas_add_node 執行前 | 自動 compass_seek(該檔案/該操作)，命中卡片注入該輪 context（fail-open） |
| **撞牆時** | 任何工具 success=0 連續 ≥2 次 | 自動 compass_seek(該工具名)，命中則附在下一次錯誤回報裡 |
| **開工時** | AgentLoop 冷啟動 / 新對話首輪 | 注入「器官地圖摘要卡」（Layer0 瘦身版，~250 tokens） |

### 3.2 出診的紀律（防泛濫）

- 注入上限：每輪最多 3 張卡（超過=扣分項，逼檢索精準）
- 全部 fail-open：羅盤壞了不擋任務，但必留錯誤痕跡
- 注入內容計入 token 帳（沿用 BudgetLedger），每季覆盤注入命中率（被注入的卡有沒有被用上）

### 3.3 intent_index 上膛

Lazy seed 改為**啟動即 seed**（首次呼叫才播種＝永遠不會被呼叫的死鎖，本次實證）。種子詞表從 155 詞按新藥箱擴充，seedVersion 沿用滾動升級機制。

## 4. 長藥：傷口自癒循環（Wound-to-Medicine Loop）

```
工具失敗(success=0)
   ↓ causal_ledger 記錄（已有）
   ↓ 【新】自動立案：pending pitfall（症狀=context_digest，藥方=空）
   ↓ agent 修復成功（同工具後續 success=1 且脈絡相近）
   ↓ 【新】compass_propose 帶「這次怎麼解的」自動草擬藥方
   ↓ 人審（or 信任曲線高 tier 自動通過）→ 入庫成為正式坑卡
```

- 立案去重：同工具同症狀 7 天內不重複立案
- 信任曲線掛鉤：tier≥3 的夥伴其 propose 可自動入庫（自律換自由，同 Agent 自律架構）
- 藥有保存期限：坑卡 90 天未被觸發命中 → 降權（不刪除，記憶鐵律）

## 5. 驗收與指標

### 5.1 殺手級驗收（Blue 定調，2026-09-17 拍板）

重演教練模式：同樣叫小橋修一個功能，**三層驗收**：

1. **行為層**：patch 前他的 context 是否自動出現羅盤卡；輪次數對比上次（上次 79 次讀檔）
2. **結果層**：修好了沒、驗證證據鏈完整
3. **自癒層（新增，Blue 拍板）**：修復過程中遇到的新問題，**治癒循環系統必須不靠 agent 動手、自己長出藥來**——事後查羅盤，應看到本次測試產生的新坑卡（pending→草擬→入庫全鏈自動），而不是等我（小葵）手動補寫。**自癒層沒過＝羅盤只是比較會說話的圖書館，不算軍醫。**

### 5.2 羅盤健康儀表（新增羅盤器官 `compass.self`）

- **諮詢率**：compass_seek 呼叫數 / 總工具呼叫數（目標：被動出診後 context 注入率 100%，主動查詢率也應上升）
- **覆蓋率**：有藥器官 / 全器官；咽喉點器官覆蓋 = 100%
- **藥效**：出診卡被注入後，同工具再失敗率下降幅度
- **藥箱飽和度**：紅隊出題（30 題常見傷）可解率 ≥90%
