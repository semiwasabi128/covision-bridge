# 橋樑 App UI 系統強化報告：融合 Buzz 與 Grok Bot 的作業模式

> 日期：2026-09-08
> 性質：競品研究 × 優化方案設計（純報告，未動 code）
> 來源：github.com/block/buzz（README/ARCHITECTURE/VISION_AGENT.md）、x.ai/news/introducing-grok-bot、block.xyz 官方公告——全第一手資料

---

## 一、兩個系統的本質

| | **Buzz**（Block, Jack Dorsey） | **Grok Bot**（xAI/SpaceXAI） |
|---|---|---|
| 一句話 | 人與 agent 共居的開源工作區（Nostr relay 上的一個房間） | 有自己電腦、24/7 在線的 AI 隊友團隊 |
| 核心隱喻 | 「Agents are members, not bots」——agent 是頻道裡的正式成員 | 「Message it like a teammate」——像傳訊息給同事一樣派工 |
| 技術底盤 | Nostr 簽名事件流：訊息/reaction/工作流/git event 全是同一種可搜尋的事件 | 雲端電腦 + 瀏覽器操作 + 外掛連接器，bot 之間可互相傳訊 |
| 開放性 | Apache 2.0 開源、可自架、model-agnostic | 閉源雲服務（Cursor 訂閱制） |
| 上市 | 2026-07-21，32.2k stars | 2026-08-11 beta |

**Blue 的直覺是對的**：兩者都在做「把 AI 從工具升級為同事」，而且介面哲学驚人地一致——**對話即工作、agent 有身份、人只做判斷題**。這正是橋樑 App 的畫布＋夥伴＋Agent Loop 已經在走的方向。

## 二、他們各自做對的事（值得偷的招）

### Buzz 的五個殺手級設計

1. **單一事件流（One event log）**
   訊息、reaction、工作流步驟、code review 批准、git event——全部是同一種簽名事件，進同一個搜尋索引。「搜對話、搜補丁、搜工作流執行、搜批准紀錄，在一個地方」。
   → *UI 意義：使用者不需要知道「資料住在哪個系統」，只有一個搜尋框。*

2. **Receipts 文化（答案附收據）**
   「問專案一個問題，agent 搜六個月歷史，回你的是 thread 和證據，不是 vibes。」
   → *UI 意義：agent 的回答永遠附出處連結，可點開追溯。*

3. **身份即權限（Scoped by identity, not permission flags）**
   「Agent 有自己的金鑰、自己的頻道成員資格、自己的審計軌跡——像界定一位隊友那樣界定它，而不是一堆 permission 開關。」
   → *UI 意義：權限管理 = 成員管理，不是設定頁的地獄開關矩陣。*

4. **誠實狀態表（Works today / Being wired up / Strong opinions, pending code）**
   README 直接用三欄表格告訴你什麼能用、什麼在接線、什麼只是想法。「請不要拿 💭 欄位規劃你的合规計畫。」
   → *這根本就是我們的 UI 誠實鐵則（壞 token 必顯失敗寧紅字不假成功）的產品級版本。*

5. **Branch as room（分支即房間）**
   開一個 feature branch → 自動長出一個頻道，補丁、CI、review、merge 決策全住在同一個房間。「頻道變成『這段程式碼為什麼存在』的紀錄。」
   → *脈絡即空間：工作發生在哪，討論就自動出現在哪。*

### Grok Bot 的五個殺手級設計

1. **零學習曲線派工**
   「不用先建 workflow 和 routine，直接傳訊息給 Bot 就完成了。」用戶證言：「就像 chatting with a friend。」
   → *對話框就是全部的 UI——沒有「先去設定頁」這件事。*

2. **參謀長模式（Chief of staff）**
   一個總管 Bot 坐鎮，下面各專科 Bot（收件匣/招募/修 bug/營運）。「不是多個你要管的 agent，是一個能平行作業的小團隊，你不再是中間人。」
   → *八爪章魚：每隻手各自做事，全部照你的方式。*

3. **Bot 群聊自治**
   把多個 Bot 放進同一個 thread，「他們自己傳遞工作、指派擁有者，只在需要判斷時才拉你進來」。
   → *人只收 judgment call，不當人肉路由器。*

4. **Teach a task（示範一次，永遠會）**
   你做一遍流程，Bot 在旁邊看，存成 routine，下次自己跑。「我示範過一次，現在完全信任它永遠跑下去，效率 2-3 倍。」
   → *把「示範」變成最自然的自動化建立方式。*

5. **信任隨時間成長（Trust your Bots with more over time）**
   「幾個任務後，它學會你的語氣、你的 edge case、什麼時候該 ping 你、什麼時候繼續做。」初期微管理 → 後期放手。
   → *進步式自主（progressive autonomy）是產品核心承諾，不是設定選項。*

## 三、對照橋樑 App：我們已有什麼、缺什麼

### 我們已經領先的（對方做不到的）

| 我們的優勢 | Buzz 對應 | Grok Bot 對應 | 誰贏 |
|---|---|---|---|
| **本地主權**：本地模型、金鑰匙多 provider、Token 自由 | 自架 relay 可比，但 agent 仍靠雲端 LLM | ❌ 純雲、閉源、單一安全邊界 | **橋樑** |
| **鐵三角記憶**：畫布＋大腦圖譜（26k 資產）＋向量庫 GraphRAG | 搜六個月頻道歷史（文字） | Bot 各自記憶（黑箱） | **橋樑**——我們的「receipts」可以指向資產本體，不只是對話 |
| **視覺共視畫布**：人機在同一張畫布上看見同一件事 | 有 canvas 但無 resident LLM 共視 | ❌ 無共享視覺空間 | **橋樑**（真實圖像思考的主場） |
| **自律架構**：BudgetLedger＋付費閘門＋工作流體檢＋信任方程式 | Approval gates 還在「接線中」🚧 | 有 approval 邊界但無記帳/預報概念 | **橋樑**——「完全的自由來自於完全的自律」就是 progressive autonomy 的可實作版本 |
| **羅盤規則中心**：三層所有權、規則即資料、append-only 軌跡 | 無對應（規則散在程式碼） | ❌ | **橋樑** |
| **開源 SemiDAO 生態** | 同為開源（Apache 2.0） | ❌ 閉源 | 平手（Buzz）／勝（vs Grok Bot） |

### 我們落後的（差距清單）

| # | 差距 | 對方 | 我們現況 |
|---|---|---|---|
| G1 | **對話即派工的零摩擦** | Grok Bot：傳訊息=完成派工，無需建任何東西 | 畫布對話已可白話操盤，但「不開畫布、純聊天完成任務」的路徑仍要繞 |
| G2 | **Agent 身份的一等公民化** | Buzz：agent 有金鑰、成員資格、審計軌跡 | 夥伴有人格與對話綁定，但無獨立身份/簽名/審計概念 |
| G3 | **單一搜尋涵蓋一切** | Buzz：一個框搜全部事件 | 搜尋分散（對話/資產/記憶各查各的） |
| G4 | **Receipts UI**（答案附出處） | Buzz：回答必附 thread 證據 | recall 有命中標記，但「回答→可點開的證據鏈」未成為 UI 慣例 |
| G5 | **多 agent 群聊自治** | Grok Bot：Bot 互傳工作、自行指派 | 有多 agent 共視頭像 chip，但無「他們自己協調、只拉我判斷」的房型 |
| G6 | **Teach a task（示範錄製）** | Grok Bot：看一遍存 routine | 畫布範本要手動存（template sync），無「看我做→自動存」 |
| G7 | **誠實狀態的產品化呈現** | Buzz 三欄誠實表 | 我們有紅字誠實鐵則，但無「這功能成熟度」的視覺分級 |

## 四、優化方案：七刀

設計原則：**不抄他們的殼，借他們的「作業方式」，用我們的引擎（鐵三角＋共視＋自律架構）去承載。** 每一刀都標註：解決哪個差距（G#）、借鑑來源、用我們什麼優勢強化。

### 第 1 刀：隊友訊息流（Teammate Inbox）— 解 G1、G5
把主對話頁升級為「隊友收件匣」：
- 每個夥伴＝一個隊友頭像，點開即對話；**派工不需要打開畫布**——白話說「幫我把這週農場照片整理成週報」，夥伴自己在背景開畫布、建工作流、跑完、回來交付。
- 畫布從「必須先去的操作場所」降級為「想看過程時才去的共視場所」。這是 Grok Bot「沒有東西要學，就在跟朋友聊天」的精髓，但我們的 agent 有真實的本地記憶和付費自律，不是黑箱雲 bot。
- **Blue 你已經有的優勢直接吃下去**：Agent Loop 的 canvas_place 操盤能力已完備，這刀主要是 UI 入口與訊息路由，不是新引擎。

### 第 2 刀：夥伴身份卡（Companion Identity Card）— 解 G2
夥伴系統升級為 Buzz 式成員模型：
- 每個夥伴一張身份卡：**自己的人格、自己的對話史、自己的審計軌跡（做過什麼、花多少、成功幾次）、自己的權限範圍**。
- 權限不是設定頁開關矩陣，而是「這個隊友可以進哪些房間、動哪些資產」的成員式管理——跟羅盤的雙層所有權（事實自動採集/意義人擁有）直接對齊。
- 審計軌跡數據源＝BudgetLedger 已經在記的帳＋工作流體檢紀錄——**資料都在了，缺的只是「以隊友為單位」的呈現**。

### 第 3 刀：全局收據搜尋（Receipts Search）— 解 G3、G4
一個搜尋框涵蓋：對話、畫布節點、大腦資產、記憶、工作流執行紀錄：
- 這正是 Buzz「one event log」的價值，但我們的版本更強：Buzz 只能搜文字事件，我們的 receipt 可以**點開直接跳到大腦圖譜裡的那顆星、畫布裡的那個節點**——搜尋結果不是連結，是空間座標。
- Agent 回答的 UI 慣例：凡引用記憶/資產，必附「📍為什麼亮」式的出處 chip（大腦圖譜第四行判讀已有此設計，推廣到全部對話）。
- 底層：鐵三角的向量庫＋GraphRAG 是現成的，缺的是跨域聯合搜尋層與統一結果 UI。

### 第 4 刀：房間即工作（Room-per-Work）— 解 G5，借 Buzz「branch as room」
- 每個進行中的任務自動長出一個「房間」：對話流＋該任務的畫布縮圖＋產出物＋審計軌跡，同屏共居。
- 多夥伴可被邀進同一房間，**他們互相傳遞工作（訊息流可見），只在 judgment call 時 @Blue**——Grok Bot 群聊自治 + 我們的多 agent 共視泡泡（頭像跟 speakerId 走）合體。
- 人類看到的不是 N 個 agent 的 N 個視窗，是一個房間裡的協作實況。

### 第 5 刀：示範錄製（Show-once Routine）— 解 G6
- 「教學模式」：Blue 在畫布上做一遍流程（或下達一輪指令），系統錄下節點/連線/參數的誕生序列，一鍵存為範本＋排程。
- 對接現有 vault_templates 回寫機制＋scheduling engine——**範本不再靠 agent 手動 sync，靠「看我做」自動生成**。
- Grok Bot 的 teach-a-task 靠錄螢幕畫面；我們錄的是**結構化操作事件**，重播更精確、可編輯、可 diff——這是我們能做得比它好的地方。

### 第 6 刀：信任成長曲線 UI（Trust Meter）— 解 G7，強化我們的自律架構
把「信任方程式（額度∝透明度×自律紀錄÷打擾程度）」變成看得見的產品：
- 每個夥伴一條信任進度：初期逐筆確認 → 體檢通過率高、浪費率低 → 自動放寬額度（Phase C progressive autonomy 的 UI 化）。
- 搭配 Buzz 式誠實分級：功能成熟度三態標記（✅可用／🚧接線中／💭設計中），全 App 統一語言——「UI 誠實鐵則」從錯誤顯示推廣到能力宣示。

### 第 7 刀：SemiDAO 開放層（Open Bridge Layer）— 戰略刀
- Buzz 證明了「開源人機工作區」有巨大市場拉力（32k stars / 三週）。橋樑的差異化宣言：**Buzz 把人機協作放上 Nostr；我們把人機共視＋本地主權放上橋樑**。他們的 agent 靠雲端 LLM；我們的 agent 用你的金鑰匙、你的本地模型、你的大腦。
- 中期可考慮：事件層相容 Nostr 簽名格式（或至少 export），讓橋樑房間的審計軌跡可被 Buzz 生態讀取——**為全人類搭橋，包括跟 Buzz 搭橋**。

## 六、一句話總結

**Grok Bot 贏在「像隊友一樣派工」的零摩擦，Buzz 贏在「agent 是有成員身份的室友」的開放架構；橋樑 App 已經握有他們都沒有的引擎——本地主權＋鐵三角記憶＋共視畫布＋自律架構——缺的只是把入口從「畫布優先」翻轉成「對話優先」，讓人只做判斷題，橋樑做所有的事。**
