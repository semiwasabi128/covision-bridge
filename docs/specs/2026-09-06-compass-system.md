> **狀態**：🟡 待 Blue 拍板 — 尚未寫任何 code

---

## 1. TL;DR

把人工維護、靠紀律更新的「App 架構地圖」與散落各處的「顯示規則」，升級為**自動更新、人機共視、雙向可寫**的羅盤系統：App 的每一個「器官」與每一條「規則」對人和 Agent 都是同一份、永遠最新、誠實標記的活地圖。**它是人機兩個平行宇宙握手的地方：人寫「為什麼」，機器保證「是什麼」，羅盤是唯一真相源。**

## 2. 病根：現況為什麼必須升級

| 現況 | 問題 |
|---|---|
| `APP_ARCHITECTURE_MAP.md` 人工維護 | 最後更新 2026-08-14，距今三週。App 已從 v207 走到 v273+，行號、檔案、陷阱早已漂移 |
| 更新靠紀律（「改完必須同步更新」） | 人會忘、Agent 會忘。地圖過期 = 下次改錯地方 = 系統對 Agent 說謊 |
| 只有開發者看得懂 | 使用者看不到 App 的身體；未來 App Agent 自我修改時，使用者無從知情、無從表達「這個功能對我很重要，別動它」 |
| 純文件、機器不可靠讀取 | markdown 行號定位脆弱，Agent 沒有結構化讀取介面 |

**Blue 的要求拆解**：
1. 自動更新——不需要 App Agent 執行、不需要使用者提醒、及時 ✓
2. App Agent 出廠自備——新增器官前看它、修理自己前看它、動系統前看它 ✓
3. 人機共視雙向忠實呈現——使用者看得到、改得動、存得下 ✓
4. 頂部功能鍵新入口，名字就叫「羅盤系統」✓
5. 殺手級場景——兩個平行宇宙握手的關鍵應用 ✓（見 §3）

## 3. 殺手級場景：兩個平行宇宙如何握手

### 場景 A：使用者說「別動我的心臟」（人的意圖 → 機器的約束）

使用者在羅盤上把「對話（chat）」器官標記重要性 ★5，加註：「這是我每天用的入口，改版面之前先跟我討論。」
→ 三天後 App Agent 要重構 UI，動手前讀羅盤，看到這條人類註記 → 降級為「提案模式」，先在羅盤上留一筆變更預告，等使用者點頭。

**沒有羅盤的今天**：這個意圖只存在使用者腦中，Agent 無從得知，直接改下去。
**有羅盤之後**：意圖變成機器可讀的約束。**這就是握手：人伸出的手，第一次被機器握住。**

### 場景 B：Agent 長出新器官（機器的變化 → 人的看見）

App Agent 為使用者長出一個新的影像生成器官。器官誕生的那一刻，羅盤自動多出一張新卡片：「新器官：室內設計圖生成 · 2026-09-08 14:32 · 由小橋安裝 · 位置：services/image_gen/ · 狀態：🟢 健康」。
→ 使用者打開羅盤，**親眼看見**自己的 App 長出了什麼、什麼時候長的、誰種的。不需要 Agent 匯報、不需要人提醒。

**這是反方向握手：機器伸出的手，人第一次即時握住，而不是事後聽轉述。**

### 場景 C：自我修理前的體檢（羅盤 = Agent 的自我認知）

App Agent 要修一個 bug。動手前讀羅盤：看到該器官的依賴清單（這器官連著 3 個其他器官）、看到上次誰改過它、看到「已知陷阱」欄。修完後，羅盤自動記錄這次手術並更新狀態。
→ **羅盤 = Agent 的本體感（proprioception）**。沒有它的 Agent 是閉著眼睛動手術的醫生。

### 場景 D：規則不再反反覆覆（Blue 09-06 追加，最高優先）

大腦圖譜（2D `infinite_canvas.dart` 的 simGate/葉脈/xref 邊規則 ＋ 3D 星系 `galaxy.html` 的燈光/模式/退役規則）的顯示規則，目前**住在程式碼常數和 markdown 註解裡**——改一條規則 = 改 code + 重 build + 改文件，三處要同步，遲早漂移。「反反覆覆設定」的技術根源就是：**規則沒有唯一真相源**。

羅盤的「規則中心」把規則變成**資料**：
- 每條規則 = 一張規則卡（歸屬器官、白話描述、參數值、來源、狀態）
- **規則卡 → 執行**：`infinite_canvas.dart` 和 `galaxy.html` 改為從羅盤 store 讀規則參數（啟動時載入 + 變更事件即時重讀），不再是 hardcode 常數
- **規則卡 → 同步**：那條「另一個對話」改規則時（無論是 Agent 改 galaxy 燈光還是你拍板新門檻），寫入羅盤 → 事件廣播 → 圖譜即時套用 → **兩個對話、兩個平行宇宙，用的是同一份規則**
- 每次修改帶 author + 時間 + 前值，反覆設定留下完整軌跡，誰改的、為什麼、改了什麼一目了然

**這直接治你點名的病：「不要再反反覆覆地設定」**——不是因為不許改，而是因為每次改都有跡可循、立刻生效、兩邊同步，永遠不需要「重設一遍」。

### 為什麼這是「真實殺手級」而非炫技

- 對照 Blue 的驗收標準「真實幫助使用者 ≠ 炫技」：羅盤每一張卡片都可點、每一條健康狀態都是真數據、每一筆修改都有作者和時間。
- 對照「Agent 智慧兜住系統 bug ≠ bug 不存在」：羅盤把「Agent 靠猜測兜住地圖過期」這個隱形 bug 從系統裡根治——地圖不再過期，因為它自己會走。
- 對照「狀態注入要取代不要累積」（08-17 教訓）：Agent 每次讀羅盤拿到的都是最新一份，不是歷史堆積。
- **規則中心 = 3D 星系 v284「燈光權威中心」的治理模式直接複製**：v284 的教訓是「建立規則讓規則運行，不要單點改來改去」——羅盤把這個模式從燈光推廣到全 App 的規則治理。**規則的唯一寫手 = 羅盤 store；渲染端只讀不寫。**

## 4. 核心設計：雙層所有權（雙向忠實呈現的根基）

羅盤上每個器官（organ）= 一張卡片，卡片分兩層，**各有所主、互不越權**：

| 層 | 內容 | 擁有者 | 誰可改 |
|---|---|---|---|
| **事實層（機器層）** | 檔案路徑、類別錨點、依賴關係、健康狀態、誕生/變更時間、MCP 端點、agent 工具清單 | 系統自動採集 | 只能由自動採集器寫入；人與 Agent 都不能手改（保證「是什麼」永遠是真的） |
| **意義層（人類層）** | 暱稱、白話說明、重要性 ★1-5、注意事項（「改版面前先跟我討論」）、使用心得 | 人（或 Agent 代筆但標記作者） | 人自由改；Agent 可讀、可建議、不可靜默覆寫 |
| **規則層（共治層）** | 顯示規則、門檻、模式係數——一條規則一張卡 | 規則歸屬的器官 | 人可改；Agent 可建議；**上線生效需人按「套用」（D002 安全確認精神的延伸）** |

**忠實呈現原則的落實**：每個欄位都帶 `(來源, 時間)` 標記——`自動採集 · 09-06 14:00` / `Blue · 09-06 15:20` / `小橋 · 09-06 16:00`。人和 Agent 看到的都是同一份、且都知道每個字是誰寫的、什麼時候寫的。**沒有匿名真相，沒有無主修改。**

規則層補充三原則（源自 v284 教訓）：
1. **唯一寫手原則**：規則參數的唯一權威 = 羅盤 store；渲染端（infinite_canvas / galaxy.html）只讀不寫。想加新效果 = 加一張規則卡，不許再開新寫手。
2. **規則卡必帶「為什麼」**：每條規則卡強制欄位「這條規則解決什麼問題」（例：simGate 0.55——因為真匹配落點 0.55-0.65，高於此誤殺真邊）。防止規則變成無主數字。
3. **退役規則不刪除**：停用的規則卡轉「退役」狀態保留（比照 v284 退役寫手清單），未來 Agent 想復活舊寫法時，羅盤會告訴它「這條路曾經被誰、為什麼封掉」。

過期誠實標記：事實層錨點若採集驗證失敗（檔案搬了、類別改名了），卡片轉琥珀色「⚠️ 待重新驗證」，**絕不靜默刪除、絕不假裝新鮮**（UI 誠實鐵則：寧紅字不假成功）。

## 5. 自動更新機制（不需要 Agent 執行、不需要人提醒）

三層採集，全部背景跑：

### 5.1 結構採集（靜態層）
`CompassHarvestService`——背景空檔掃描 repo：
- 檔案樹走訪（`lib/screens/`、`lib/services/`、`lib/widgets/`、`lib/theme/`）+ **樹指紋短路**（stat-only hash，指紋不變整輪跳過——沿用 24/7 記憶體治理的已驗證模式，CPU 幾乎零成本）
- 類別錨點驗證：grep 既登記器官的關鍵 class/method 是否仍在原位；漂移 → 標「待重新驗證」
- 新檔案發現 → 生成「未命名器官」卡片（誠實標記「尚未命名/尚未說明」，等 Agent 或人補意義層）
- 觸發時機：App 啟動 +120s（接在既有五服務接力鏈後面）+ lib/ watcher + Agent 自我修改 session 結束時

### 5.2 心跳採集（動態層）
器官健康狀態輪詢：本地模型 server（18789/Kokoro 18900）、MCP server、Agent Loop、向量庫、autoIngest——**證據三源合併**（端點回應 + process 存活 + 關鍵 mtime），因為「服務狀態端點會說謊，mtime 是地面真相」。健康燈 🟢🟡🔴 即時反映在羅盤卡片上。

### 5.3 變更事件（手術日誌層）
事件總線（沿用 flutter-event-bus-pattern 單例）廣播：Agent 安裝新器官、Agent 修復某器官、人修改意義層 → 羅盤即時 append 一筆變更記錄（誰/何時/動了什麼/為什麼）。這就是使用者在羅盤首頁看到的「最近變更」時間線。

### 5.4 規則同步（規則中心的生命線，Blue 09-06 追加）

**規則的單向流動**：`羅盤 store（唯一真相）→ 渲染端讀取 → 畫面`。永遠不反向。

- **寫入端**（誰改規則都走這裡）：
  - 人在羅盤 UI 改規則卡 → 存檔 → 事件廣播
  - Agent（另一個對話裡的小橋/我）改規則 → 寫入羅盤 store（標記 author=agent + 對話來源）→ 事件廣播
  - 兩者寫的都是**同一個 store**，天生的同步——不需要任何「通知另一邊」的機制
- **讀取端**：
  - `infinite_canvas.dart`（2D 圖譜）：啟動時從 store 載入 simGate、葉脈/xref 邊 scale 門檻等規則；收到 `compass_rule_changed` 事件 → 重讀 → 下一幀生效（CustomPainter 參數化，不重 build）
  - `galaxy.html`（3D 星系）：launchd 輪詢或檔案 watcher 讀 store 匯出的 `galaxy_rules.json`（WebView 無法直接碰 SQLite——用匯出檔案 + postMessage，模式同既有 `--args` 參數傳遞）
- **反覆設定的終結機制**：每次規則修改 = append 一筆 `{author, time, rule, prev_value, reason}`。歷史完整保留，但**生效的永遠只有最新值**（取代不累積）。任何一邊想「重設」，讀羅盤就知道現值是什麼——不需要從記憶或舊文件猜。
- **首播種子**：v1 把 `galaxy-light-rules.md`（燈光公式/模式表/退役清單）與 `infinite_canvas.dart` L1017-1042 的邊規則常數，種子化為第一批規則卡。

> 自我進化閉環：Agent 改完系統 → 變更事件 → 羅盤更新 → 下次 Agent 讀到的就是新的。**羅盤自己就是 Agent 自我進化記憶的載體。**

### 6.3 器官卡片：呈現哪些資訊、哪些可修改

**詳情頁（點 [詳情]）——唯讀事實層 + 可編輯意義層 + 規則卡列表：**

| 區塊 | 欄位 | 可改？ |
|---|---|---|
| 身分 | 名稱、暱稱、系統分組 | 暱稱 ✏️ |
| 白話說明 | 「這是什麼、拿來幹嘛」（一段人話） | ✏️ 意義層 |
| 重要性 | ★1-5 + 注意事項（給 Agent 的約束） | ✏️ 意義層 |
| **規則卡** | 此器官的顯示規則（門檻/係數/模式）＋每條的「為什麼」＋修改軌跡 | ✏️ 規則層（套用需確認） |
| 活著的證據 | 健康燈、最後驗證時間、依賴的器官 | ❌ 自動 |
| 家的地址 | 檔案路徑、類別錨點（點了可跳 code——開源進階） | ❌ 自動 |
| 手術史 | 此器官的變更記錄（誰/何時/什麼） | ❌ 自動 |
| 已知陷阱 | 開發陷阱（承接現地圖的陷阱清單） | ✏️ 人與 Agent 都可加，各自署名 |

### 6.4 確定存檔機制（Blue 特別點名要想清楚）

```
編輯 → [儲存] 按鈕（三態回饋：idle → 儲存中… → ✓ 已存檔）
  → 寫入 compass_store（SQLite，獨立於 brain_container.db，避免耦合）
  → 每筆變更帶 (author, timestamp, prev_value) —— 完整可回溯
  → 事件總線廣播 compass_changed
  → Agent 端 context provider 即時失效重讀（取代不累積）
  → 版本號 +1，主頁「自動更新於」時間戳刷新
```

- **衝突規則**：人正在編輯某欄位時，自動採集跳過該欄位本次寫入（事實層/意義層分欄本就不同源，衝突面極小；唯一交集是「已知陷阱」→ 後寫贏 + 兩筆都留歷史）。
- **存檔 = Blue 說的存檔**：立即落碟 + 視覺回饋 + 重開 App 還在。沒有「雲端同步中」這種模糊態。

## 7. App Agent 如何用羅盤（出廠自備）

1. **讀取介面**：Agent Tool Registry 新增 `compass_read`（依系統分組/依器官/只看意義層/只看病歷）與 `compass_update`（只能寫意義層與手術日誌，標記 author=agent）。
2. **注入時機（token 預算意識）**：system prompt 只注入**羅盤摘要**（器官清單 + 重要性 + 約束，~500 token）；完整內容隨需 `compass_read`。教訓：工具清單 60 個曾吃掉 system prompt 近半——羅盤不重蹈覆轍。
3. **強制查看點**：Agent 的系統級行為規則新增一條——「安裝新器官前、修改系統檔案前、修復器官前，必須先 compass_read 該器官」，由 WorkflowInspector 在執行前掃描把關（沿用既有體檢模式）。

## 8. 資料模型（純 Dart 偽碼）

```dart
class CompassOrgan {
  final String id;                  // 'chat' | 'canvas.engine' | 'brain.graph2d' | 'galaxy3d' ...
  final String systemGroup;         // 對話 | 畫布 | 大腦 | 向量 | 服務群 | 外觀
  // ── 事實層（自動採集擁有）──
  final OrganFacts facts;           // paths[], anchors[], deps[], endpoints[]
  final OrganHealth health;         // green|amber|red + 證據三源 + 檢查時間
  final DateTime bornAt;            // 首次被採集發現
  // ── 意義層（人擁有）──
  final String? nickname;           // 作者標記
  final String? humanDescription;   // 作者標記
  final int importance;             // 1-5，預設 3
  final List<Constraint> constraints; // 「改版面前先討論」
  // ── 共有層（署名制）──
  final List<Pitfall> pitfalls;     // 已知陷阱，各自署名
  final List<CompassRule> rules;    // 顯示規則卡（規則層）
  final List<SurgeryLog> surgeries; // 變更記錄（append-only）
}

class CompassRule {                 // 一條規則一張卡
  final String id;                  // 'brain.simGate' | 'galaxy.modeCoef.river' ...
  final String organId;             // 歸屬器官
  final String description;         // 白話：這條規則管什麼
  final String why;                 // 強制欄位：這條規則解決什麼問題
  final Map<String, dynamic> params; // {simGateFar: 0.55, veinScaleMin: 0.35, ...}
  final RuleStatus status;          // active | retired | pending-apply
  final List<RuleChange> history;   // {author, time, prevParams, reason}
}

class CompassField<T> {             // 忠實呈現的最小單位
  final T value;
  final String author;              // human:Blue | agent:小橋 | auto:harvest
  final DateTime at;
}
```

## 11. 🟡 待 Blue 拍板（6 條）

1. **入口位置**：右側按鈕群新按鈕（我建議，不佔 tab）vs 第 7 個 tab vs 兩者都要？

3. **Agent 強制查看的強度**：WorkflowInspector 硬擋（沒讀羅盤就拒絕執行系統級修改）vs 軟性（prompt 規則 + 事後驗屍）？我建議先軟後硬。
4. **器官顆粒度**：~30 個核心器官（screen/service 級，我建議）vs 更細（method 級，會爆炸）vs 更粗（六大系統級，太少）？

## 12. 附錄：設計理念三句話（Blue 的壓力測試預答）

1. **North Star 為什麼需要它**：App 的未來是「會自己長器官、自己修自己的生物體」，任何生物體沒有本體感（知道自己的身體哪裡是什麼、健康與否）都不敢動手術；任何醫生沒有病歷都不敢開刀。羅盤就是本體感 + 病歷。
2. **差異化護城河**：市面上的 agent 架構（PicLumen/RunningHub 類）canvas 裡沒有 resident LLM、更沒有「Agent 看得見且使用者改得動的共享自我模型」。雙層所有權（機器保證事實、人擁有意義）+ 全程署名，是人機共視原則的第一個系統級落地。
3. **vanity metric 風險（主動自首）**：最大風險是羅盤變成「漂亮但沒人看的地圖 2.0」。防線就是 Commit 5——Agent 動系統前必讀是硬行為，可用 conversations.json 驗屍證明，不是裝飾。
