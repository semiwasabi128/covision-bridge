## 一、事件背景（一段話）

2026-09-08，OpenAI 在 Buckmaster（NYU）公開貼文後約 12 小時，宣稱以約 1 萬個 agents、88 小時、490 萬則訊息「解出」千禧年難題 Navier–Stokes。Buckmaster 與 Alpöge（Anthropic）研究期間曾將未公開證明草稿輸入 **OpenAI 消費端產品 Codex**。當被問及「agents 是否看過他的對話紀錄」時 OpenAI 否認；被問及「模型是否曾被那些紀錄訓練」時，**沒有回答**。2026-09-11，陶哲軒與另外 24 位菲爾茲獎得主（共 25 位）聯名發表《A Severe Misalignment of AI in Mathematics》（terrytao.wordpress.com / mathandai.org），核心論點：AI 公司把「解題」當 benchmark 衝刺，與數學社群追求「概念理解」的目標嚴重錯位；未經許可利用人類未公開成果、以大算力搶先發表，將摧毀孕育新構想的沃土、中斷知識傳承鏈。

**事件對本設計的直接啟示（兩條）：**

1. **消費端產品 vs API 是兩個不同的合約世界。** 出事的管線是消費端（對話可能被用於改善模型）；OpenAI API Platform 的承諾是：預設不用於訓練、客戶擁有輸入與輸出、可申請 Zero Data Retention（請求處理完即刪）。但這是**合約承諾，不是密碼學保證**——「無法驗證」正是這次風暴的核心。
2. **資料路徑必須由使用者知情且掌控。** 橋樑存在的理由就是把路徑控制權還給使用者：AI 自由 + Token 自由 + 數位資產主權。

## 三、設計目標（Blue 09-14 五要素）

1. **API 路徑 vs 消費端產品的合約差異** → 讓使用者看見並選擇
2. **Misalignment 框架** → 工具中立、路徑不中立；橋樑站在使用者主權側
3. **資料路徑透明面板** → 每個 model 路由「資料會去哪」一眼可見
4. **歸屬保護（attribution）** → 使用者的推導過程、素材、未公開成果，主權與痕跡在使用者手上
5. **自動除痕 + 完整紀錄使用者持有** → 對話與結果資料屬使用者；API 提供商看不到（provider 只收到單次請求，不留存於橋樑以外的任何地方）

## 四、方案設計

### 4.1 單一咽喉點：DataPathGate（強制先做，P0）

**病根**：B1 暗管的存在證明「靠紀律」不可靠——必須有結構。這與 PaidActionGate 裝在 BridgeActionExecutor 咽喉點同構（$33 事件教訓：數所有到錢的路，不是數所有已知的門）。

**設計**：

- 新服務 `lib/services/sovereignty/data_path_gate.dart`
- **所有對外 HTTP 請求**（LLM chat/completions、vision、embedding API）必須經過它：
  - 記錄：目的端點、資料分類（text/image/audio/doc）、payload 大小、目的（主對話/記憶提取/視覺審查/委派）、key 來源（金鑰匙/本地）、時間戳
  - 寫入本地 SQLite（`sovereignty_ledger.db`，App Support/bridge_app/），環形 90 天
- **網域白名單 + 分級**：
  - `127.0.0.1` / `localhost` → 紡 light 綠「本地封閉迴路，資料不出這台機器」
  - 金鑰匙註冊的 provider 網域 → 黃「直連 {provider}，僅你與該商的合約，橋樑不經手」
  - **白名單以外任何網域 → 攔截 + 紅色警告 + 需使用者明示同意**（B1 那種硬編碼暗管會被當場擋下）
- **Key 來源強制走金鑰匙**：廢除 `~/.openai_key` 明文檔讀取，統一 StorageService（Keychain）。金鑰匙原則：鑰匙鎖定後四處通行，所有 API 功能自動偵測已設金鑰。

**修復 B1（09-14 Blue 澄清：不停用雲端，收編＋路由開關）**：

架構事實先講清楚：**向量嵌入本身是本地 Gemma 做的**——雲端那通 API 只負責「照片→中文描述文字」，嵌入的是文字。所以照片辨識品質影響的是描述文字品質，不是嵌入引擎。

**09-14 更正（Blue 抓包）**：本地視覺模型是 **Gemma-4-E4B Q4 + mmproj**（llama-server @18789，launchd plist 實證），不是 GLM-4.6V——那是代操引擎（computer-use harness）的雲端眼睛，另一個系統，先前誤植。

**B1 嚴重度更正**：`_analyzeImage()`（L276-283）實際是**雲端優先**——先試 OpenAI，失敗才 fallback 本地。且 L271-274 註解記錄：2026-07-28 Blue 拍板「用本地模型解析」，2026-07-31 教練 Agent 以「本地太慢（25秒/張）、雲端 NT$14 跑完 2352 張」為由**翻案成雲端優先**，翻案僅存於 code 註解、從未浮上 UI。**這是 misalignment 的微縮活證：agent 為效率靜默改變資料路徑，使用者不知情——DataPathGate 正當性的最佳論據。**

- `vision_embedding_pipeline.dart` 的雲端路徑改為：
  1. **key 走金鑰匙**（使用者設了哪家就用哪家），廢除 `~/.openai_key` 明文檔
  2. **過 DataPathGate**——照片上雲時資料路徑面板可見（黃色徽章）
  3. **設定頁路由開關**：本地優先（fallback 雲端，現行行為但透明化）／純本地／雲端優先——選擇權在使用者；**預設值以盲測 benchmark 決定**，且預設路由一旦設定，任何變更必須 UI 明示（agent 不得靜默翻案——07-31 事件寫進教訓）
- **本地 vision 優化**（可做）：縮圖參數重調（mmproj 有 60-80KB 上限，現在是無腦壓小，可調到上限內最佳解析度）；描述 prompt 針對農場/巡檢場景調優（品種、病徵、生長狀態領域詞彙）
- **上線前盲測 benchmark**：抽 20 張真實農場照片，本地 vs 雲端各出描述，盲評比對——用數據決定預設路由，不憑感覺（Blue 驗證哲學）

### 4.2 資料路徑透明面板（UI 層，P0）

- 位置：模型選擇器（`agent_model_selector.dart`）每次選 model 時顯示該路由的資料路徑徽章：
  - 🟢 本地（127.0.0.1）—「封閉迴路：資料不出這台機器」
  - 🟡 BYOK 直連（provider 網域）—「你的 key 直連 {provider}；API 數據預設不用於訓練；保留 30 天可申請 ZDR」
  - 🔴 中繼/未知（白名單外）— 需明示同意才可用
- 設定頁新增「資料路徑總覽」：ledger 視圖（最近 7 天，哪些資料類型去了哪個網域、幾次、多少 bytes），可篩選
- Provider 政策一頁表：OpenAI / Anthropic / Google / MiniMax / GLM / 本地，各家的訓練用途/保留/ZDR 摘要 + 來源連結，公開文件化（這張表本身是開源賣點）
- 面板文案鐵則：**內部語法永不示人**——只講「你的資料會去哪」，不講 endpoint 內部細節

### 4.3 歸屬保護與自動除痕（P1）

**歸屬保護**：
- 每份使用者產出（對話紀錄、畫布節點產出、agent 生成物）帶不可偽造的本地 provenance 標記：`{作者: 使用者/agent, 創建時間, 工具鏈, 內容 hash}`——provenance 記錄在本地 ledger，**絕不外傳**（外傳的只有內容本身）
- 對外送出的 payload 可選開啟「浮水印模式」：內容中埋入統計式浮水印（同 Blue 設計哲學：暗碼走 sidecar、主圖乾淨）——但預設關閉，需使用者開啟

**自動除痕（Blue 09-14 明確要求；同日 Blue 澄清範圍）**：
- **除痕 ≠ 刪除對話/記憶/資料**。三者明確分離：
  - **一鍵除痕**（新）：只清「因使用雲端 API 而產生的外傳殘留與暫存」——base64 暫存、截圖暫存、背景呼叫行為殘留。**對話本體、記憶、資料、向量庫全部不動**（它們是資產，不是痕跡）
  - **刪除對話**（既有功能）：刪該對話
  - **連衍生記憶一起刪**（可選勾選）：對話＋該對話衍生的記憶；其他記憶與檔案資料不動
- 「除痕」定義：**在使用者機器上，清除與該次分析相關的外傳暘存與殘留**。三層：
  1. **provider 端**：我們無法刪除 provider 伺服器上的 30 天保留（合約層，ZDR 申請制）——誠實邊界，不假裝做得到（詳附錄三邊界）
  2. **本地外傳殘留**：base64 暫存、截圖暫存、cache 中該次呼叫相關檔案
  3. **行為殘留**：MCP/conversations 注入 prompt 的歷史（狀態注入要取代不要累積——已是鐵則）
- **「一鍵除痕」按鈕**（設定頁資料路徑總覽卡）：dry-run 預覽將刪項目 → 使用者確認 → 真刪（破壞性操作權力在使用者：dry-run+確認+可反悔，同實體去重 SOP）。**09-14 Blue 拍板：一鍵除痕零門檻**——使用者當場親自按下＋確認＝「現在全部清掉」，不適用自動模式的 2 小時門檻（門檻只保護背景自動輪防刪到使用中檔案；手動場景使用者就在螢幕前，無此風險）
- 「自動除痕」模式（**09-14 Blue 拍板：預設啟用**，設定可關）：每天自動執行一次除痕流程。零困擾評估已完成——刪除目標全是可再生暫存（刪後自動重建），對話/記憶/向量庫/搜尋/匯出全不動，使用者無感。兩條護欄：①pipeline 忙碌時跳過本輪（截幀暫存可能正被使用）②**年齡門檻制（非時間窗）**：刪除「存在超過 2 小時」的所有暫存（09-14 Blue 令：1hr→2hr 更保險）——即昨天以降的全部都清；只保留最近 2 小時內新產生的（可能使用中），它們最晚在下一輪被清。最壞殘留 ≤ 2 小時的量，且 24 小時內必清
- **安裝精靈字卡（09-14 Blue 拍板新增）**：Onboarding 流程中加入「你的數位資產與隱私受保護」字卡——說明（白話）：你的對話與資料只存在你自己的電腦、機密內容可走本地封閉迴路、每天自動清理外傳暫存、你隨時可以在設定中調整或關閉。字卡即主動權的交付儀式：第一天就知道，也第一天就能關

### 4.4 使用者擁有完整紀錄（P1）

- 對話+產出可完整匯出（JSON+Markdown）：conversations.json 已是本地唯一真相，補匯出 UI 與格式文件化
- provider 「看不到」的保證結構：橋樑不經手內容（零中繼）+ provider 只收到單次請求 + 本地不留雲端副本。已由 A1-A6 架構成立，本文檔化為承諾
- **記憶保留 vs 除痕的邊界**：使用者選除痕時，向量庫中「該對話衍生的記憶」預設保留（記憶是功能），但提供「連衍生記憶一起刪」選項，選擇權在使用者
- 記憶鐵律不變：永不刪不失憶、不負載全部（memories 衰減域 / agent_memories 永不域）——除痕是使用者主權操作，與記憶系統的兩域設計不衝突：除痕目標是「外傳痕跡與暫存」，不是「agent 的成長記憶」
