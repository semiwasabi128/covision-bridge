### 缺口（本系統要補的）

1. **併發執行未驗證**：TaskDispatcher 結構上支援多 session，但從未三線同時跑過——撞車點（下節）沒有防護
2. **無會議機制**：agent 之間沒有「坐下來講」的場合——各自跑完只進帳本，不會互相看到
3. **無情報共享池**：工作中發現的情報（线索、坑、外部資訊）只活在各自的對話 context 裡，會隨壓縮消失
4. **無互相挑戰/複盤**：沒有紅隊輪替、沒有複盤產物
5. **單一活躍夥伴**：9/21 拍板「活躍 Agent=手動切換、切夥伴必走 UI」——**前台對話維持此原則不變**，本系統是**背景任務層**的多人化，不違反拍板

## 三、系統設計（三層）

### 層一：執行層——不撞車的三條線

```
Blue（下令）
  └─ TaskDispatcher（唯一派工台）
       ├─ Session A → Agent 甲 + 工作畫布 A + 租約表
       ├─ Session B → Agent 乙 + 工作畫布 B + 租約表
       └─ Session C → Agent 丙 + 工作畫布 C + 租約表
                  ↓ 全部
            AgentStatusStore（D1 狀態單一真相源，live/unverifiable/exited）
                  ↓ 訂閱
       sidebar / 任務卡 / 懸浮窗 /（未來手機）
```

- 狀態走 D1（§3.6 已定案）：一個 store 全 reader 訂閱，三線 100 線同一套
- 租約表放 TaskDispatcher 內（`Map<String, Lease>`），獨佔資源（build/git）先租後用
- 每條線的房間四象限照舊——鐵則不變

### 層二：情報層——共享情報池

- 新增 `lib/services/collab/intel_pool.dart`：輕量 JSON/SQLite 表
- 欄位：`id / fromAgent / kind（坑/線索/外部情報/成果預告）/ content / relatedSession / createdAt / consumedBy`
- 寫入時機：agent 工作中主動寫（工具 `intel_share`）＋任務收尾自動摘要一筆
- 消費時機：會議前全量注入；新任務派工時注入相關（按 relatedSession/kind 過濾）
- **主權對齊**：情報池是 agent 產物，入帳本蓋章（誰寫的可考）

### 層三：會議層——開會/檢討/挑戰/複盤

**會議 = 一種特殊的 TaskSession**（不另建通道，鐵則一的勝利）：

- 與會者：三 Agent（各帶自上次會議以來的 ledger 摘要＋情報池新條目）＋主持人（腦：旗艦模型）
- 會議議程（固定四段）：
  1. **回報**：各自 30 秒——做了什麼、帳本數字、遇到的坑
  2. **挑戰**：紅隊輪替——每次會議指定一名 agent 當挑戰者，質疑其他兩人的做法（Blue 紅隊哲學的制度化）
  3. **情報**：情報池未消費條目逐條處置——採納進誰的任務/歸檔/丟棄
  4. **決議**：產出行動項→ 透過 TaskDispatcher 派工（決議直接變成新任務，**會議不是聊天是派工的前置**）
- 產物：會議紀錄進帳本＋決議寫羅盤（collab 器官規則可被會議更新）
- 觸發：定時（每週）＋事件（任務失敗/撞車防護觸發/情報池滿 N 條）

### 指揮鏈：各帶 10 人

- 三 Agent = 軍官；`delegate_batch` = 派兵工具（已存在）
- 軍官的 system prompt 加「指揮官守則」：拆工、派兵、驗收、彙整回報——不自己做完所有事
- 指揮鏈在畫布上 = delegation 邊（D3）——會議層看到的是三個軍官，執行層看到的是 30 個工位

## 六、開戰閘門（M4 鐵則——2026-09-22 Blue 令）

> 「啟動集群作戰時，Agent 必須貫徹打破砂鍋問到底的邏輯——跟使用者討論到
> Agent 自己都沒有問題了、使用者也都沒有問題了；作戰計畫出來、作戰地圖
> 也有了、戰術也有了、需要什麼工具什麼武器都準備好了，才開始動手。
> 任意開戰都是災難。」
> —— grill-me 哲學的戰爭版：100 個兵的資源，一個錯誤假設就放大一百倍。

### 六道關卡（全過才開戰，缺一不可）

| 關 | 名稱 | 內容 | 完成判準 |
|---|---|---|---|
| G1 | **終點定義（以終為始）** | 先定義「打完長什麼樣」：可驗證的終點現實（交付物是什麼、在哪、怎麼驗收）、成功判準、失敗判準。**沒有可驗證終點的戰爭不開打**——乒乓非接力，終點不是「大家做完了」而是「現實改變了且驗得出來」 | 使用者認可終點與驗收方式 |
| G2 | **作戰意圖對齊** | 軍官重述目標＋邊界＋「不做什麼」，使用者點頭 | 使用者說「對」 |
| G3 | **作戰計畫** | 拆解成軍團結構：幾軍、各軍任務、依賴關係、預估兵力 | 使用者看過計畫無異議 |
| G4 | **作戰地圖** | 計畫放上畫布——軍官節點＋兵節點骨架＋指揮鏈邊（D3），開戰前先看見戰場 | 使用者看過地圖無異議 |
| G5 | **戰術武器＋成本代價評估** | 每軍用什麼工具/模型/順序；**成本試算表**：預估兵數×輪數×token 單價＝金錢成本、預估牆鐘時間、DGX 負載、失敗重打成本（打輸一次賠多少）；關鍵工具先試射——**武器壞的不開戰，帳算不清的不開戰** | 試射通過＋使用者看過成本數字無異議 |
| G6 | **雙向零疑問** | 軍官反問使用者剩下的問題（打破砂鍋）→ 使用者反問 → **雙方都說「沒有問題了」** | 雙向明確確認 |

### 成本評估的會計原則

- **試算表必列**：金錢（雲端腦 token 費）、時間（牆鐘估計）、算力（DGX 佔用）、**失敗半徑**（中途喊停已燒多少、重打一次全額多少）
- **上限欄**：使用者可設這場戰爭的花費上限——超出即停戰回報（不是默默繼續燒）
- **戰後對帳**：running 結束後實際開銷 vs 試算表並列（多退少補的誠實——記進 BudgetLedger，跟其他帳同一本）
- 依據：Blue 會拿先前結論對帳新數字——**報數字必分解成分、精確歸因**，試算表不給總額糊弄

### 實作機制

- **狀態機**：`SwarmCampaign` 物件，狀態 `planning(G1-G6) → committed → running → reviewing → done`。**只有 committed 之後才允許 spawn 兵**；`delegate_batch` 在 planning 狀態被呼叫 = 硬拒絕（誠實回覆「作戰計畫未過閘門」）
- **閘門由使用者推進**：每道關卡是一則對話輪——Agent 呈現→使用者回覆→過關或修正。不是計時器不是自動過關
- **隨時可棄案**：planning 任何時刻使用者說「不打了」→ 整案丟棄，零成本零殘留（此時還沒有任何兵被派出）
- **試射（G4）**：關鍵工具在單兵模式先跑一次（例如生圖工具先產一張試試）——武器壞的不開戰
- 與 M3 會議的關係：開戰閘門的討論發生在**對話輪**（軍官與使用者），會議層（agent 之間）是 running 之後的執行協調——兩者不混淆

### 呈現對位（偵察結論 2026-09-22：Kimi/AgentsRoom/Orca 三家掃描）

- **L1 對話流實況**（Kimi 式）：白話下達大目標→planning 五關在對話裡走→開戰後實況卡（派兵數/各軍進度）
- **L3 兵團卡**（AgentsRoom 卡片網格精神×房間四象限）：任務卡展開=兵團格，每兵一格狀態燈
- **L2 畫布星系**（橋樑獨有，另立 M5）：兵=光點、軍官=亮恆星、指揮鏈=連線——「同一片海」美學的戰場版

## 五、不變式（每條都是鐵則）

1. 三鐵則不變：任務通道=TaskDispatcher、展示=房間四象限、記帳=Ledger＋蓋章
2. 前台拍板不變：活躍夥伴切換走 UI（9/21）——本系統全程在背景任務層
3. 主權不變：情報池/會議紀錄/決議全部入帳本可審計；破壞性操作權力在使用者
4. 誠實不變：兵的產出由軍官驗收、軍官的回報由會議挑戰——兩層驗證不省略
