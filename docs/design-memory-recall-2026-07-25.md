# 記憶回溯機制設計（方案 A：關鍵字回溯 + 迭代精進）

> **一句話**：當使用者抱怨 Agent 失憶時，從完整對話歷史中搜尋相關內容，注入 context 讓 Agent「找回記憶」。搜尋不準時，使用者的追 complain 會成為下一輪搜尋的線索，越找越準。

---

## 一、問題分析

### 為什麼會「失憶」

```
完整對話歷史（conversation.messages）← 從未刪除，一直都在 disk 上
    ↓ ContextCompressor
最近 12 則 + 舊訊息壓縮成摘要 ← LLM 只看到這些
```

LLM「失憶」不是資料不見了，而是被壓縮摘要丟掉了細節。使用者抱怨時，其實資料就在腳下。

### 使用者的真實需求

使用者要的不是「完美的記憶」，而是 **「東西還在」的安全感**：
- ✅ 「我幫你找回來了」— 安心
- ✅ 「這些是找到的，還有遺漏嗎？」— 被重視
- ✅ 「請放心，我會把它找回來」— 被負責
- ❌ 「抱歉我忘記了」— 恐慌（東西是不是不見了？）

---

## 二、整體流程

```
使用者訊息進入
    ↓
① 失憶抱怨偵測（是抱怨還是普通對話？）
    ↓ 觸發
② 關鍵字萃取（從使用者的抱怨中抽出搜尋線索）
    ↓
③ 全歷史搜尋（在 conversation.messages 中搜尋）
    ↓
④ 結果排序與格式化（按相關度排序，格式化為 system note）
    ↓
⑤ 注入 context（讓 LLM 帶著找回的記憶回覆）
    ↓
⑥ Agent 回覆（帶有「找回來了」的語氣 + 確認機制）
    ↓
⑦ 迭代精進（如果使用者說「不是這個」→ 用新線索重新搜尋）
```

---

## 三、各步驟詳細設計

### ① 失憶抱怨偵測

**目標**：判斷使用者是否在抱怨 Agent 忘記了某事。

**偵測策略**：雙層判斷

**第一層：模式匹配（快速、零成本）**

```
觸發詞列表（持續擴充）：
- 直接抱怨型：「你忘記了」「你忘了」「你不是記得」「你之前說過」「我之前講過」「不是跟你說過」
- 疑問型：「你記得嗎？」「你還記得嗎？」「你不記得了？」
- 比較型：「之前明明就」「上次你還說」「怎麼跟上次不一樣」
- 失憶指控型：「失憶」「健忘」「記性差」「金魚腦」
```

**第二層：上下文增強（降低誤判）**

不是所有「記得」都是抱怨失憶：
- 「你記得明天要開會嗎」→ 這是提醒，不是失憶抱怨
- 「你忘記了我要用 MiniMax」→ 這才是失憶抱怨

判斷規則：
- 觸發詞 + **負面語氣詞**（了、不是、明明、還、怎麼）→ 高機率是抱怨
- 觸發詞 + **疑問句尾**（嗎、吧）且不含負面詞 → 可能是測試或提醒，不觸發
- 觸發詞 + **具體名詞**（專案名、工具名、人名）→ 高機率是抱怨，且自帶搜尋關鍵字

**設計決策**： 寧可誤觸發也不要漏觸發。誤觸發只是多做一次本地搜尋（零成本），漏觸發則讓使用者覺得「AI 真的失憶了」。

### ② 關鍵字萃取

**目標**：從使用者的抱怨句中抽出有效的搜尋線索。

**這是精準度最關鍵的環節。** 使用者抱怨時的句子結構通常是：

```
「你忘記了 [關於 X 的事]」
「我之前說過 [Y]」
「不是跟你說過要 [Z]」
「上次討論的 [W] 呢」
```

**萃取策略**：

**A. 停用詞過濾**

```
停用詞（不搜尋這些）：
- 代名詞：你、我、他、它、這個、那個、這些、那些
- 動詞（泛）：說、講、提、討論、忘記、記得、知道
- 連接詞：的、了、是、就、才、還、也、都、不
- 語氣詞：嗎、吧、呢、啊、喔
```

**B. 保留詞（高價值關鍵字）**

```
優先保留：
- 專有名詞：MiniMax、OpenAI、GLM、橋樑計畫、GraphRAG...（英文/品牌名）
- 數字/日期：7/23、300萬、第二步、第三階段...
- 中文名詞片語：鹿角蕨、氣象、晨間拾穗、紙上交易...
- 否定詞後的名詞：「不是 OpenAI 是 MiniMax」→ 保留 OpenAI + MiniMax
```

**C. 句型模板抽取**

```
模板 1：「你忘記了 X」→ 抽 X
模板 2：「我之前說過 X」→ 抽 X  
模板 3：「不是 Y 是 Z」→ 抽 Y + Z（兩個都是線索）
模板 4：「上次討論的 X 呢」→ 抽 X
模板 5：「你之前 [動詞] 了 [什麼]」→ 抽 [什麼]
```

**D. 前一輪上下文輔助**

如果使用者連續抱怨（迭代場景），上一輪的搜尋結果和 Agent 回覆也是線索：
```
第一輪：「你忘記了我要用 MiniMax」→ 關鍵字：MiniMax
Agent 回覆找到了 MiniMax 相關內容
使用者：「不是這個，是那個 OpenAI 的設定」→ 關鍵字：MiniMax + OpenAI + 設定
                                                       ↑ 上一輪的  ↑ 新的
```

### ③ 全歷史搜尋

**目標**：在 `conversation.messages` 中搜尋包含關鍵字的訊息。

**搜尋範圍**：
- 只搜尋「不在最近 12 則裡」的訊息（最近 12 則 LLM 已經看得到，不需要回溯）
- 搜尋 `role == 'user'` 和 `role == 'assistant'` 的訊息

**搜尋策略**：

**A. 多關鍵字 OR 搜尋**

```
關鍵字：[MiniMax, OpenAI, 設定]

訊息 1（user）：「我要用 MiniMax 不要 OpenAI」→ 命中 MiniMax + OpenAI（2 命中）
訊息 2（assistant）：「好的，已切換到 MiniMax...」→ 命中 MiniMax（1 命中）
訊息 3（user）：「設定好了嗎」→ 命中 設定（1 命中）
訊息 4（user）：「MiniMax 的 key 怎麼用」→ 命中 MiniMax（1 命中）
```

**B. 命中數排序**

```
排序規則：
1. 命中關鍵字數量多的優先（訊息 1 命中 2 個 → 排第一）
2. 同命中數時，較新的訊息優先（使用者可能記得最近的）
3. user 訊息優先於 assistant（使用者說的話比 AI 說的更重要）
```

**C. 上下文擴展**

找到命中訊息後，**連帶取回前後各 1~2 則訊息**，因為：
- 使用者的需求通常是一段對話，不是單則訊息
- 「我要用 MiniMax」的下一則 AI 回覆（「好的，已切換」）是重要上下文

```
命中：訊息 5（user）：「我要用 MiniMax 不要 OpenAI」
擴展取回：
  - 訊息 4（assistant）：「目前使用的是 OpenAI...」
  - 訊息 5（user）：「我要用 MiniMax 不要 OpenAI」  ← 命中
  - 訊息 6（assistant）：「好的，已切換到 MiniMax，API key 已設定...」
```

**D. 去重與截斷**

- 同一輪對話（user + assistant）如果多則都命中，合併成一個「片段」
- 最多取回 5 個片段（控制 context 用量）
- 每個片段截斷到 500 字（保留頭尾，中間省略）

### ④ 結果排序與格式化

**目標**：把搜尋結果格式化為 LLM 能理解的 system note。

**格式**：

```
【記憶回溯】
使用者似乎認為你忘記了某些內容。以下是從完整對話歷史中找回的相關段落，
請參考這些內容回覆使用者。語氣要讓使用者安心——東西還在，你找回來了。

---

📌 片段 1（7/23 14:05，命中關鍵字：MiniMax、OpenAI）
👤 使用者：我要用 MiniMax 不要 OpenAI
🤖 助理：好的，已切換到 MiniMax，API key 已設定...

---

📌 片段 2（7/23 14:12，命中關鍵字：MiniMax）
👤 使用者：MiniMax 的 key 怎麼用
🤖 助理：請到設定頁面...

---

📌 片段 3（7/22 09:30，命中關鍵字：設定）
👤 使用者：設定好了嗎
🤖 助理：還沒，我需要你提供...

---

💡 回覆指引：
- 如果這些就是使用者指的內容，確認你找回來了：「我找回來了，你之前說的是...」
- 如果不完全對，誠實說：「我找到了這些，是你要找的嗎？如果不是，請給我更多線索」
- 如果沒找到，負責任地說：「我暫時沒找到，但資料一定還在。請問大概是什麼時候討論的？或者提到什麼關鍵詞？」
```

**關鍵設計：回覆指引**

這段指引是讓 LLM 知道「找到時怎麼回、找不到時怎麼回」。這直接決定了使用者感受到的是「安心」還是「恐慌」。

### ⑤ 注入 Context

**注入位置**：在 `ApiService.sendMessage` 的 system note 區塊，跟其他 note 並列。

```
final finalSystemContent = [
  systemContent + modelIdentityNote + handoffNote,
  ?compressedContext.systemNote,      // ← 壓縮摘要
  ?insightRecallNotes,
  ?secondBrainMemoryNotes,
  ?brainNotes,
  ?memoryRecallNote,                  // ← 新增：記憶回溯
].join('\n\n');
```

**Token 預算**：回溯 note 控制在 1500 字以內（5 個片段 × 300 字）。這不會讓 context 爆掉，因為壓縮摘要本身已經在控制總量了。

### ⑥ Agent 回覆語氣設計

這不是程式碼問題，是 prompt 設計問題。在回覆指引中明確定義三種情境：

**情境 A：找到了，而且就是使用者要的**

```
語氣：安心 + 確認
「我找回來了！你之前說的是 [具體內容]。我會把這個記在上下文裡，不會再忘了。」
```

**情境 B：找到了一些，但不確定是不是使用者要的**

```
語氣：負責 + 邀請確認
「我從之前的對話中找到了這些：[片段摘要]。是你要找的嗎？
如果不是，跟我說更多線索（大概是什麼時候？提到什麼？），我再找找看。」
```

**情境 C：沒找到（搜尋結果為空）**

```
語氣：負責 + 安心保證
「我暫時沒找到，但請放心——我們的對話記錄都還在，只是我一時沒搜到。
你可以給我更多線索嗎？例如大概什麼時候討論的？或者提到什麼名詞？
我一定會幫你找回來。」
```

### ⑦ 迭代精進（核心亮點）

**這是整個方案的靈魂。** 第一次搜尋不準沒關係，使用者的追 complain 自帶更多線索。

**迭代流程**：

```
第一輪：
  使用者：「你忘記了我要用 MiniMax」
  關鍵字：[MiniMax]
  搜尋結果：5 個片段（可能有干擾項）
  Agent 回覆：「我找到了這些...是你要找的嗎？」

第二輪（使用者追 complain）：
  使用者：「不是這個，是那個 OpenAI 的設定問題」
  偵測：這是迭代抱怨（「不是這個」+ 新關鍵字）
  關鍵字：[MiniMax, OpenAI, 設定] ← 保留舊的 + 加入新的
  排除：第一輪已經回覆過的片段（使用者說「不是這個」= 排除）
  搜尋結果：更精準的片段
  Agent 回覆：「找到了！是這個...」

第三輪（如果還不夠）：
  使用者：「對，就是這個，但還有一個關於 API key 的」
  偵測：部分確認 + 補充搜尋（「還有一個」= 新關鍵字）
  關鍵字：[MiniMax, OpenAI, 設定, API key]
  搜尋結果：API key 相關片段
  Agent 回覆：「這個也找到了！[片段] 還有遺漏嗎？」
```

**迭代狀態管理**：

需要在 session 中維護回溯狀態：

```dart
class MemoryRecallSession {
  /// 目前累積的關鍵字（每輪迭代追加）
  List<String> accumulatedKeywords = [];
  
  /// 已經回覆過的片段 ID（使用者說「不是這個」= 排除）
  Set<String> excludedMessageIds = {};
  
  /// 已經確認找到的片段（使用者說「對就是這個」= 保留）
  Set<String> confirmedMessageIds = {};
  
  /// 迭代次數（用於調整搜尋策略）
  int iterationCount = 0;
  
  /// 是否處於回溯模式（連續抱怨 = 回溯中）
  bool isActive = false;
  
  /// 最後一次活躍的時間（超過 5 分鐘沒新抱怨 = 回溯結束）
  DateTime? lastActiveAt;
}
```

**迭代偵測規則**：

```
「不是這個」/「不對」/「不是」 → 排除上一輪結果，重新搜尋
「對」/「就是這個」/「沒錯」   → 確認找到，檢查是否還要繼續
「還有」/「另外」/「以及」     → 補充搜尋，保留已確認的
「還有遺漏嗎」/「就這些嗎」   → 使用者問 Agent → Agent 主動再搜一次
```

**迭代超時**：如果使用者 5 分鐘內沒有新的抱怨或追 complain，回溯 session 自動結束。下次抱怨重新開始。

## 四、補償機制（搜尋不準時）

### 補償 A：時間範圍縮小

```
第二次迭代時，如果使用者提到時間線索：
「大概是上週講的」→ 篩選 7 天內的訊息
「那天下午」→ 如果能對應到具體日期，篩選該日下午
```

### 裯償 B：LLM 輔助判斷（方案 B 作為 fallback）

```
如果方案 A 搜尋結果為空，或者第三輪迭代後仍然不準：
→ 把使用者的抱怨 + 最近被壓縮的歷史發一次 LLM 呼叫
→ 「使用者說你忘記了 X。以下是完整歷史摘要，請判斷使用者可能指什麼。」
→ LLM 回傳更精準的判斷
```

這只在方案 A 失敗時觸發，不會每次都花 token。

### 補償 C：主動回報搜尋過程

```
Agent 回覆時可以透明化搜尋過程：
「我用 'MiniMax' 和 'OpenAI' 在你的對話歷史中搜尋，
找到了 3 個相關片段。如果不是你要的，可以告訴我：
- 大概是什麼時候討論的？
- 有沒有提到其他名詞？
- 是在聊天頁面還是畫布頁面討論的？」
```

這讓使用者感覺到 Agent **真的在努力找**，而不是敷衍。

### 補償 D：跨對話搜尋（未來擴展）

```
如果當前對話找不到，可以搜尋其他對話：
「在這個對話裡沒找到，但我在你另一個對話 '7/22 設定討論' 裡找到了相關內容：
[片段]
是這個嗎？」
```

這需要搜尋 `ConversationStore.getAll()` 的所有對話，成本稍高但不是不可能。

## 五、精準度提升策略

### 策略 1：關鍵字加權

```
不是所有關鍵字同等重要：
- 專有名詞（MiniMax、GraphRAG）→ 權重 3
- 數字/日期（7/23、300萬）→ 權重 2
- 一般名詞（設定、設定、key）→ 權重 1
- 否定詞後的名詞 → 權重 +1（使用者特別強調「不是 X」= X 是重要線索）
```

### 策略 2：訊息類型加權

```
user 訊息的命中 > assistant 訊息的命中
（使用者記得的是自己說過的話，不是 AI 的回覆）
```

### 策略 3：時間衰減

```
較新的訊息略微優先（使用者通常記得最近的）
但不是絕對——有時候使用者記得的是很久以前的事
衰減係數：每 7 天權重 ×0.9（不是硬截斷，是軟偏好）
```

### 策略 4：語境擴展搜尋

```
不只搜尋關鍵字本身，也搜尋關鍵字的「語境同義詞」：
「MiniMax」→ 也搜「minimaxi」「MM」「image-01」
「設定」→ 也搜「配置」「config」「設定頁」「API key」
```

這需要一個簡單的同義詞表，可以用 hardcode 或讓 LLM 在第一次碰到時建立。

## 六、實作架構

### 新增檔案

```
lib/services/memory_recall_service.dart     ← 核心服務
lib/services/memory_recall_session.dart     ← 迭代狀態管理
```

### 修改檔案

```
lib/services/api_service.dart               ← 注入回溯 note
lib/controllers/chat_controller.dart         ← 維護回溯 session
```

### 核心類別

```dart
/// 記憶回溯服務 — 無狀態，可被多個對話共用
class MemoryRecallService {
  /// 偵測使用者是否在抱怨失憶
  static bool isMemoryComplaint(String userMessage);
  
  /// 從抱怨句中萃取關鍵字
  static List<RecallKeyword> extractKeywords(
    String userMessage, {
    List<String>? previousKeywords,  // 迭代時帶入
  });
  
  /// 在完整對話歷史中搜尋
  static List<RecallFragment> search(
    List<Message> allMessages,
    List<RecallKeyword> keywords, {
    Set<String>? excludedMessageIds,  // 迭代排除
    int maxFragments = 5,
  });
  
  /// 格式化為 system note
  static String? buildRecallNote(List<RecallFragment> fragments);
}

/// 回溯關鍵字
class RecallKeyword {
  final String word;
  final double weight;  // 權重 1~3
  final KeywordType type;  // properNoun, number, commonNoun, negatedNoun
}

/// 回溯片段（一則命中的訊息 + 上下文）
class RecallFragment {
  final String messageId;
  final DateTime timestamp;
  final String role;  // user or assistant
  final String content;  // 截斷後的內容
  final List<String> hitKeywords;  // 命中了哪些關鍵字
  final double score;  // 總分
  final List<Message> context;  // 前後各 1~2 則訊息
}
```

### 整合點

在 `ApiService.sendMessage` 中，現有的流程是：

```
messages → _compressContextForChat → systemNote + messages → LLM
```

新增回溯後：

```
messages → _compressContextForChat → systemNote + messages
                                        ↓
                         isMemoryComplaint(lastUserMessage)?
                                        ↓ Yes
                         extractKeywords → search → buildRecallNote
                                        ↓
                         recallNote 加入 systemNote → LLM
```

## 七、邊界情況處理

| 情況 | 處理 |
|---|---|
| 對話太短（<12 則）| 不觸發 — 還沒被壓縮，不會失憶 |
| 使用者連續抱怨 3 次都找不到 | 升級到方案 B（LLM 輔助） |
| 使用者抱怨但沒有具體關鍵字（「你怎麼都忘了」）| Agent 回：「請給我更多線索，大概是什么時候的事？」 |
| 畫布對話 vs 一般對話 | 畫布對話也走同樣機制（共用 ApiService） |
| 跨對話搜尋 | 第一版不做，作為未來擴展 |
| 找到的內容太長 | 每片段截斷 500 字，最多 5 片段 |
| 迭代超過 5 次 | Agent 建議開新對話重新描述需求 |

## 八、成功指標

| 指標 | 目標 |
|---|---|
| 失憶抱怨偵測率 | >90%（寧可誤觸發） |
| 第一次搜尋命中率 | >60%（找到使用者要的） |
| 迭代後最終命中率 | >85%（兩輪內找到） |
| 使用者主觀感受 | 「東西還在」的安全感 |
| 額外 token 成本 | 0（純本地搜尋，方案 B fallback 才花 token） |

## 九、實作優先順序

1. **Phase 1（MVP）**：偵測 + 關鍵字萃取 + OR 搜尋 + 注入 + 基本回覆指引
2. **Phase 2**：迭代精進（排除已回覆片段 + 累積關鍵字）
3. **Phase 3**：關鍵字加權 + 時間衰減 + 語境同義詞
4. **Phase 4**：方案 B fallback（LLM 輔助判斷）
5. **Phase 5**：跨對話搜尋
