## 1. 從「共視」到「共識」——缺失的一環

共視宣言定義了三層：共同看見 → 共同感覺 → 共同建造。

但 使用者 指出了更精準的鏈條：

| 階段 | 人做什麼 | AI 做什麼 | 畫布上發生什麼 |
|---|---|---|---|
| **共視** | 看見同一個節點 | 處理同一個節點 | 注意力重疊 |
| **共識** | 理解 AI 為什麼這樣做 | 理解人為什麼這樣選 | 雙方的理解開始對齊 |
| **互補** | 補上 AI 的盲點（直覺、脈絡、美感） | 補上人的極限（記憶、計算、路徑探索） | 畫布上出現雙方都沒單獨想到的東西 |
| **加速** | 比獨自做更快、更準、更有創意 | 比單向執行更精準命中人的意圖 | 產出的品質和速度都提升 |

**共視 ≠ 監控。共視是為了共識，共識是為了互補，互補是為了加速。**

## 2. 真正的共視/共識機制長什麼樣

### 2.1 目前橋樑有什麼

已有的：
- Canvas 同步狀態（人看到節點，Agent 看到同一張圖）
- Agent Event Bus（Agent 發出「我在做什麼」的事件）
- Annotation layer（人在畫布上畫標記）
- Transurfing 水流／門（共識過程的視覺化）

缺的（這份文件要設計的）：
- **AI 的注意力是可見的** — Agent 正在看哪個節點、在思考什麼，即時呈現在畫布上
- **人的意圖是可被 AI 感知的** — 人標記、選取、停留的行為，不只是 UI 操作，是對 Agent 的信號
- **共識形成的過程是可看見的** — 不是「AI 跑完 → 人看結果」，而是「AI 提議 → 人反應 → AI 調整 → 人確認」的來回過程在畫布上展開
- **互補的結果有名字** — 當人和 AI 共同產出一個雙方都沒單獨想到的東西時，這個東西要被標記為「共視產物」

### 2.2 共視/共識的產品機制（4 個）

#### 機制 1：AI 注意力光暈（Agent Attention Halo）

**問題**：目前 Agent 在背景跑，人不知道它在看什麼。
**設計**：Agent 正在處理的節點上方出現一個微妙的光暈（不是粒子，是 Layer B 的視覺標記）。光暈的強度隨 Agent 處理深度變化——淺層（剛開始看）= 微光，深層（正在生成/分析）= 聚焦光。

這不是裝飾。這是讓人知道「AI 現在在看這裡」——共視的第一步。

**與設計語言的關係**：Layer B（關係推演），不是 Layer C（事件氣氛）。不能搶 Layer A。

#### 機制 2：人意圖信號（Human Intent Signal）

**問題**：Agent 不知道人正在注意什麼。
**設計**：人在畫布上的行為（停留、選取、標記 annotation）不只服務 UI，同時變成對 Agent 的意圖信號。Agent loop 可以讀取這些信號，調整自己的優先級和方向。

- 人停留在一個節點上 3 秒 → Agent 知道「人對這個感興趣」
- 人畫了一個 annotation → Agent 知道「人想強調或質疑這裡」
- 人選取兩個節點的連線 → Agent 知道「人想理解這兩者的關係」

**與 NativeAgentLoop 的關係**：`AgentEventBus` 已有事件流。新增一條「人意圖事件」流，雙向。Agent 不只 emit，也 listen。

#### 機制 3：共識往返（Consensus Rally）→ **[2026-08-25] 幽靈節點形態已裁撤，保留共識往返本質**

**問題**：目前是「人下指令 → AI 執行 → 人看結果」的單向流。
**設計**：破壞性/創造性的操作，變成「AI 提議 → 呈現 → 人接受/修改/拒絕 → AI 執行」的往返。

**[教練 Agent 2026-08-25]** 使用者 裁示：**幽靈節點（半透明 ghost node 形態）不需要**。
共識往返的精神保留，但載體是「素材池節點」（AI 產 3 條候選 → 人採用/修改/跳過），
不做獨立的幽靈節點形態。這跟 D002（安全確認 ConfirmDialog）仍然不同——
ConfirmDialog 是「你確定嗎？」，共識往返是「我覺得可以這樣，你覺得呢？」

**與 Transurfing 的關係**：水流完成判定方案 B（Agent 回覆 → awaitingConfirmation → 使用者下一句決定）就是共識往返的一個實例。這個模式已存在於對話流，素材池是它在畫布上的化身。

#### 機制 4：共視產物標記（Covision Artifact Tag）

**問題**：沒有方式區分「AI 單獨產出」和「人機共同產出」。
**設計**：當一個東西經過了共識往返（機制 3），它的 CanvasNode 被標記為 `coCreated: true`。

這個標記的用途：
- 未來的共視指標可以從 `coCreated` 節點的比例計算「建造完成率」
- Brain Reflection 面板可以顯示「今天你和 AI 共同建造了 N 個東西」
- 社群分享時可以標示「這份工作流有 70% 是人機共創的」

## 3. 指標作為副產物（不是設計目標）

當上述 4 個機制在運作時，以下信號自然產生：

| 信號 | 來源機制 | 意義 |
|---|---|---|
| 注意力重疊時間 | 機制 1 + 機制 2 | 人和 AI 同時關注同一節點多久 |
| 共識往返次數 | 機制 3 | 人和 AI 來回了多少次才達成共識 |
| 修改率 | 機制 3 | 人的修改比例（高=AI 提議不夠準，低=默契好） |
| 共視產物比例 | 機制 4 | 總產出中 `coCreated` 的比例 |
| 首次提議接受率 | 機制 3 | AI 第一次提議就被接受的比例（信任度指標） |

**這些指標不需要額外的 tracker——它們是機制運作的日誌。** 先把機制做好，指標就是讀 log。

## 4. 隱私邊界（使用者 的第二個關注）

追蹤使用者的注意力到什麼程度會變成 surveillance？

**原則**：
- ✅ 追蹤：哪個節點被注意了多久（用來幫助共識，不用來分析使用者行為）
- ✅ 追蹤：共識往返的次數和結果（用來幫助下一次提議更準）
- ❌ 不追蹤：cursor 的絕對座標軌跡
- ❌ 不追蹤：使用者在看什麼文字、停在哪個詞上
- ❌ 不上傳：所有注意力資料只在本地，不上雲、不上鏈

**設計語言對應**：[統合設計語言](BRIDGE_UNIFIED_DESIGN_LANGUAGE.md) § 3.1「功能可用性永遠第一」——注意力追蹤的目的是幫助共識，不是幫助我們分析使用者。

## 6. 與共視宣言的關係

共視宣言說了「為什麼」——人機共視是全球空白位。
本文件說了「怎麼做」——4 個機制讓共視從理念變成產品裡的真實行為。

> 共視不是看見對方在看什麼。共視是兩個意識透過看見對方在看什麼，開始理解對方為什麼這樣看，然後各自補上對方的盲點，一起走到雙方都沒單獨想到的地方。
