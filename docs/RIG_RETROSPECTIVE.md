## 1. 為什麼嘗試（2026-07 → 09 的動機）

夥伴立繪是橋樑「貼近」能力的核心載體。目標：讓小橋/MimeMi 不只是一張靜態圖，而是**有呼吸、有動作、會隨狀態變化的活體**——對應共視宣言的「共同感覺」層（Layer 2 Co-feeling：畫布把兩個意識放在同一個可回應的場域）。

時間軸（git 事實）：

## 2. 為什麼收尾（教訓）

1. **macOS AppKit 深水區成本過高**：sublayerTransform 被 backing layer 重置、anchorPoint 改了 position 必須同步補（否則立繪飛走=畫面空白）、NSImageView 架構重寫兩輪——每一關都在跟 AppKit 的未文件化行為搏鬥，不是跟產品需求搏鬥。
2. **素材工程 >> 程式工程**： carved body 手術、紙片分離診斷、手臂停用——動態 rig 需要的分層素材（每狀態、每部位、每幀）製作成本遠超預期，且品質不穩（拼接感）。
3. **性價比翻轉**：使用者感知到的「活體感」，80% 來自輕微呼吸（1.2% 縮放、3.2s 循環），20% 才來自部位級動作。為 20% 的感知付出 80% 的深水區成本，不成立。
4. **呼吸感反而更穩**：封存後的胸口呼吸/三帶分層呼吸版本，零崩潰、零黑框、像素級穩定——靜態+呼吸是「夠好且可靠」的在地最優解。

## 3. 保留什麼／放棄什麼

### 保留（重啟成本 = 1 個 flag）

- **rig v4 全部代碼/素材/規格都在庫**：`RIG_ASSET_GENERATION_SPEC.md` + NSImageView 架構
- **重啟方式**：`rigEnabled` 改 `true` 即可（`3c429e29` commit 訊息明載）
- **rigmap v2 知識**：多圓心矩形帶/雙錨點橋接——這套「運動帶」的數學直接餵養了三帶分層呼吸

### 放棄（不再投入）

- 部位級動態動畫（九狀態程序動畫）
- carved body 分層素材產線
- 跟 AppKit backing layer 的長期抗戰

## 4. 未來決策守則

1. **若未來要重啟動態立繪**：優先評估(1) 換渲染層（如 Flutter 內 widget 動畫而非 NSPanel/NSImageView 混種）(2) 素材產線是否可自動化。兩者任一無解，不重啟。
2. **任何「活體感」需求先問**：呼吸感（中心微縮放/胸口擴散/分層錨點）能否滿足 80% 感知？能，就用呼吸感路線。
3. **本復盤的存在意義**：下次有人（包括未來的我）提議「讓立繪動起來」，先讀這份文件的第 2 節。
