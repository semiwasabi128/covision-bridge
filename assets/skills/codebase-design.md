# 架構健康檢查 — 讓程式碼好維護

## 什麼時候用

- 一波開發後定期檢查
- 使用者說架構有點亂
- 開發新功能前先整理

## 檢查什麼

### 1. 檔案大小

- 超過 2000 行的檔案要考慮拆分
- 超過 4000 行的檔案一定要拆
- 拆的原則：按職責拆，不是按行數拆

### 2. 耦合度

- 兩個檔案總是一起改 → 它們耦合了
- 改 A 一定要改 B → 考慮合併或抽出共同服務
- 一個概念要看好幾個檔案才懂 → 考慮整合

### 3. 模組深度

好的模組：**簡單的介面，豐富的功能**
壞的模組：**複雜的介面，很少的功能**

- 只有轉發的 wrapper class → 太淺
- 只有資料沒有行為的 data class → 考慮把相關行為移進去
- 散在多處的相關邏輯 → 考慮集中

### 4. 命名一致性

- 同一個概念有沒有用不同的名字？
- 不同概念有沒有用相似的名字？

## 怎麼跟使用者說

**用白話，不用工程術語：**

| 不要說 | 改成說 |
|--------|--------|
| 「bridge_desktop_screen.dart 有 4800 行需要拆分」 | 「主畫面的程式碼太長了，一個檔案塞了所有功能。我建議把側邊欄、畫布頁、專案頁拆成各自的檔案，這樣以後改一個功能不用在 5000 行裡找」 |
| 「兩個 ChatController 共用 SharedPreferences」 | 「現在兩個聊天框會互相搶目前的對話 ID，我建議抽出一個管理器來統一管理」 |
| 「CanvasMetadata 是淺模組」 | 「畫布資料現在只是個資料袋，沒有任何行為。建議把存檔、載入這些操作放進去，讓它自己知道怎麼存取」 |

## 重要原則

- **一次只改一個地方** — 不要一次重構全部
- **改完要測試** — 重構後功能要照常運作
- **先得到使用者同意** — 解釋清楚為什麼要改、改什麼、影響什麼
- **不是為了漂亮而重構** — 是為了以後更好改、更少 bug
